# LiveTranslate 项目讲解稿

> 讲解时长建议：15-20 分钟 | 演示 5 分钟 | 提问 5 分钟

---

## 一、开场（2 分钟）

### 一句话概括

**LiveTranslate 是一个基于阿里云 DashScope Qwen 大模型的实时同声传译平台——边说英文，边出中文字幕。**

### 解决什么问题

跨语言沟通中有三个痛点：
1. **延迟高**：传统方案说完一句话等 5-10 秒才出翻译，对话节奏被打断
2. **不够准**：通用翻译引擎听不懂上下文，"it"/"they" 指代常常翻错
3. **不方便**：开会时要在翻译软件和会议软件之间来回切换

我们这个项目做到了：**端到端延迟 < 3 秒，上下文感知翻译，悬浮字幕任何软件上方可见。**

---

## 二、核心能力（3 分钟）

### 2.1 实时语音识别（ASR）

- 接入阿里云 DashScope **Qwen ASR Flash Realtime** 模型
- 流式 WebSocket 协议，说话的同时就在转写
- 支持麦克风和浏览器标签页两种音频采集模式

### 2.2 智能翻译（MT）

- 翻译引擎：**Qwen-Plus 大模型**，一次 API 调用同时完成翻译 + 语法纠错
- **上下文感知**：记住前两句原文和译文，代词指代不翻错
- **智能分块**：三种切分策略自动平衡延迟和语义完整度
  - 遇到标点（≥10 字）→ 立即切
  - 满 20 个单词 → 立即切
  - VAD 检测到停顿 → 立即切
- **术语表**：专业名称自动缩写，Kubernetes → k8s，Artificial Intelligence → AI
- 多层兜底：LLM 挂了自动切 MyMemory 免费 API

### 2.3 双端显示

| 端 | 技术 | 场景 |
|---|------|------|
| Web 控制台 | React + Vite | 自己看翻译结果、日志、波形 |
| 桌面字幕 | Python PyQt5 | 悬浮置顶，任何软件上方可见 |

### 2.4 桌面字幕亮点

- 无边框半透明悬浮窗，始终在最上层
- **双层显示**：上方实时预览（流式更新），下方精确翻译（LLM 纠错后）
- 自由拖动 + 右下角缩放 + 双击换色（6 种）
- 暂停/恢复按钮——只停显示不停后台
- HTTP 控制接口——远程控制显示/隐藏

## 三、系统架构（4 分钟）

### 3.1 整体架构图

```
浏览器/桌面字幕
      │ WebSocket
      ▼
┌─────────────┐
│   Gateway   │ :3000   ← 共享一条 ASR 连接，广播字幕给所有客户端
└──────┬──────┘
       │
  ┌────┴────┐
  ▼         ▼
┌──────┐  ┌───────────┐
│ ASR  │  │ Translate │
│:3001 │  │ :3002     │
│ WS   │──│ HTTP POST │
└──┬───┘  └─────┬─────┘
   │            │
   ▼            ▼
DashScope    DashScope
ASR API      Qwen-Plus
(实时流式)   (翻译+纠错)
```

### 3.2 关键设计决策（重点讲）

**决策 1：共享 ASR 连接**

Gateway 只维护**一条**到 ASR 服务的 WebSocket 连接，所有客户端共用。翻译结果广播给全体。

👉 *好处：多个客户端（浏览器 + 桌面字幕）看到的内容完全同步，不会各说各话。*

**决策 2：翻译调度在 ASR Handler 里完成**

增量翻译 2500ms 防抖 + 分块策略，最终翻译立即触发。翻译服务本身是无状态的 REST API。

👉 *好处：调度逻辑和识别流程紧密耦合，响应更快；翻译服务保持简单可水平扩展。*

**决策 3：冷却期 + 版本号防残留**

MARK_FINAL 后 800ms 冷却期内，所有增量结果被忽略。版本号递增使旧的增量翻译自动失效。

👉 *好处：防止上一句的残留碎片污染新句翻译。这是实际踩过的坑。*

**决策 4：Python 做桌面字幕**

ADR-002 明确决策：Java/Node.js 无法原生创建透明置顶窗口，PyQt5 是最佳选择。

👉 *好处：30 行 PyQt5 代码搞定，不用折腾 Electron。*

## 六、项目亮点总结（1 分钟）

1. **实时低延迟**：WebSocket 长连接 + 流式处理，不是传统的"说完一句翻一句"
2. **上下文翻译**：记住前两句，代词不翻错——这是大模型翻译相比传统 MT 的核心优势
3. **LLM 翻译+纠错一步到位**：单次 API 调用，延迟更低、口语修正更自然
4. **冷却期机制**：实际落地中发现的坑，版本号 + 冷却期双重保障
5. **双端同步**：共享 ASR 连接，浏览器和桌面字幕看到的内容完全一致
6. **一键启动**：`start.bat` 搞定一切，不需要分别配置每个服务
7. **术语表**：专业场景下的缩写转换，LLM 原生支持

## 七、可能的提问 & 回答

**Q: 为什么不用 Web Speech API 自带的翻译？**

A: 浏览器内置 API 准确率和延迟不可控，且不支持上下文翻译和专业术语表。DashScope 的 Qwen 大模型翻译质量远高于通用方案。

**Q: 延迟还能更低吗？**

A: 目前 2-3 秒的延迟主要来自三个方面：ASR 识别（~1s）、LLM 翻译（~1-2s）、网络传输（~100ms）。如果要进一步降低，可以考虑用更小的翻译模型或流式翻译（边译边出）。

**Q: 支持离线使用吗？**

A: 目前依赖阿里云 DashScope 云端 API，需要联网。离线方案可以用本地 Whisper 模型 + Ollama 翻译，这是后续可以扩展的方向。

**Q: 怎么支持更多语言？**

A: DashScope 支持 50+ 语言，在前端切换源语言和目标语言即可，后端 ASR 和翻译服务会自动适配。

**Q: 如果有多个人同时用，翻译会乱吗？**

A: 当前架构是共享 ASR 连接 + 广播模式，所有客户端看到相同翻译。如果需要多路独立翻译，需要在 Gateway 层做 session 隔离——这是架构上预留的扩展点。

## 八、结束语

LiveTranslate 从实际需求出发，解决"低延迟 + 高准确率 + 跨应用显示"三个核心痛点。技术栈上选择了最适合每层任务的工具：Node.js 做网关和服务、React 做前端、Python 做桌面悬浮窗、大模型做翻译引擎。整体架构简洁但每个细节都经过实战打磨。

**"30 行代码接入，500ms 内听到翻译结果。"**
